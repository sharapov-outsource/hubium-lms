# Локальный узел Hubium — план

## Задача

Организация (колледж, школа, филиал компании) работает с Hubium в облаке, но её интернет-канал ненадёжен: связь пропадает на минуты и часы. В это время в аудиториях не открываются материалы, срываются тесты и сдача работ.

Локальный узел — экземпляр Hubium в локальной сети организации или её филиала. Пока связь есть, он отдаёт компьютерам организации страницы, файлы и видео из локальной сети, а изменения передаёт в облако. Когда связь пропадает, узел продолжает работать сам. Когда связь возвращается, он передаёт в облако всё, что было сделано без неё. Учащиеся дома всё это время работают с облаком.

У одного облака может быть сколько угодно узлов: у каждого филиала или корпуса свой.

Технические подробности после реализации переходят в `docs/architecture.md` (на английском), а этот план удаляется, как и план сборки v1.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Продукт или разовое решение | Часть продукта: режим узла есть в каждом релизе и ставится `install-hubium.sh` |
| Главная копия данных | Облако. Узел никогда не становится главным: его изменения облако принимает как операции и проверяет своими правилами |
| Несколько узлов | С самого начала: у облака сколько угодно узлов, по одному на филиал или корпус. Каждый узел обслуживает свою сеть и теряет связь независимо от других |
| Что работает без связи | Всё содержимое курсов и все действия учащихся во всех элементах: тесты, задания, лекции, форумы, вики, глоссарии, базы данных, семинары, опросы, анкеты, SCORM, H5P, видео. Действия преподавателя (оценки, отзывы, правка курса) работают, но облако принимает их, только если там за это время не изменили то же самое. Администрирование работает только при связи |
| Адрес | Один и тот же: внутренний DNS организации направляет адрес LMS на узел |
| Вход без связи | Логин и пароль (хэши паролей есть в копии базы), двухфакторный код. LDAP — если сервер каталога в локальной сети. Внешние провайдеры (Google, Яндекс, VK, SSO) — только при связи |
| Что недоступно без связи | AI-помощник, вебинары, внешние инструменты LTI, загрузка нового видео. Почта и push уходят из облака после синхронизации |
| Порядок работы | Сначала реализуем всё, потом показываем организациям |

## Как это выглядит для людей

- **Связь есть.** Страницы, файлы и видео грузятся из локальной сети. Изменения уходят в облако и сразу видны. Для человека разницы с облаком нет, только всё быстрее.
- **Связь пропала.** Первые две минуты (настраивается) узел работает только на чтение, а автосохранение тестов повторяет попытки. Затем включается автономный режим с плашкой «Нет связи с основным сервером. Работа сохраняется на сервере организации и будет передана автоматически». Работает всё, кроме перечисленного выше.
- **Связь вернулась.** Узел ждёт, пока закончатся идущие тесты с ограничением времени. Затем на минуту-две он переходит в режим «Синхронизация» (только чтение), передаёт облаку всё сделанное и возвращается в обычный режим.
- **Облако что-то не приняло**, например тему форума закрыли из дома. Тогда операция попадает в отчёт о конфликтах, автор получает уведомление, а текст его ответа сохраняется.
- **Филиалы.** Каждый филиал работает со своим узлом под тем же адресом. Обрыв связи в одном филиале не задевает другие.
- **Недоступно само облако.** Тогда в автономный режим переходят все узлы, и занятия во всех филиалах продолжаются.

## Архитектура

### Компоненты

```
               интернет (ненадёжный)
  ┌──────────── облако ────────────┐         ┌──────────────── узел (ЛС) ────────────────┐
  │ Caddy → web, worker            │ HTTPS   │ Caddy: чтение → web узла                   │
  │ PostgreSQL (главная копия) ────┼─────────┼─▶      запись  → облако                    │
  │ хранилище файлов               │ репли-  │ web узла ─ читает A (онлайн) или B (без связи)
  │ API узлов, поток событий,      │ кация   │ PostgreSQL A: физическая реплика облака    │
  │ воспроизведение журналов,      │ по TLS  │ PostgreSQL B: каскадная реплика A,         │
  │ конфликты                      │         │   рабочая копия на время обрыва            │
  └────────────────────────────────┘         │ агент узла: режимы, зеркало файлов,        │
                                              │   синхронизация, обновления               │
                                              │ зеркало файлов (те же ключи, что в облаке) │
                                              └────────────────────────────────────────────┘
```

- **Облако** — обычная установка Hubium. К ней добавляются реестр узлов, API узлов, поток событий для узлов, воспроизведение журналов узлов и отчёт о конфликтах. PostgreSQL облака принимает репликацию узлов по TLS с клиентским сертификатом, у каждого узла свой слот репликации.
- **Узел** — тот же релиз в режиме `HUBIUM_ROLE=node`, только в Docker. Узел сам подключается к облаку, поэтому белый IP организации не нужен.

### Режимы узла

| Режим | Чтение | Запись | Фоновые задачи |
|---|---|---|---|
| Онлайн | база A | пересылается в облако | только агент узла |
| Нет связи (первые минуты) | база A | отказ с сообщением, автосохранение повторяет | только агент |
| Автономный | база B | в базу B с записью в журнал операций | внутренние задачи на B |
| Синхронизация | база B | отказ: «идёт синхронизация» | агент передаёт журнал |

Автономный режим включается сам, когда облако недоступно дольше порога. Администратор узла может включить его вручную, например в день экзамена при плохом канале. Он же может отложить синхронизацию до конца занятия.

### Онлайн-режим

- **Запись.**
  - Caddy узла пересылает в облако все изменяющие запросы: POST/PUT/PATCH/DELETE, server actions, `/api/auth/*`. GET-запросы обрабатывает web узла по базе A.
  - Облако узнаёт запрос от узла по подписанному заголовку и после фиксации транзакции ставит cookie с позицией WAL (LSN).
  - Следующий GET на узле ждёт, пока реплика A дойдёт до этой позиции: до 3 секунд, иначе запрос уходит в облако. Так человек сразу видит то, что сам изменил.
- **Server actions.** Облако и узел работают на одной сборке. Ключ шифрования server actions (`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`) сейчас нигде не задан и создаётся заново при каждой сборке. Он будет выводиться из `APP_SECRET`. Секреты (`APP_SECRET` и другие) узел получает при регистрации.
- **Запись при чтении страниц.** GET-запросы сейчас пишут в базу, а на реплике это сломается:
  - `noteUserAccess` раз в минуту (`apps/web/src/server/session.ts:38`, `packages/core/src/users/last-access.ts:16`);
  - на странице элемента — `markActivityViewed`, `recordCourseAccess` и `logEvent('activity.viewed')` (`apps/web/src/app/(app)/course/[courseId]/a/[activityId]/page.tsx:85-96`);
  - на странице курса — `recordCourseAccess`;
  - просмотр SCORM создаёт попытку (`modules/scorm/src/ui/view.tsx:74`);
  - кэш текста файлов (`packages/core/src/files/text.ts:49`);
  - `lastUsedAt` API-токенов;
  - продление сессии Better Auth раз в сутки и счётчики ограничения запросов в базе.

  Правило будет такое: GET не пишет в базу напрямую. Попутные записи (последний заход, просмотры, доступ к курсу) идут через один интерфейс `ctx.touch`. В облаке он пишет в базу как сейчас, на узле копит записи и пачками отправляет их в облако. Попытку SCORM создаёт операция. На узле Better Auth не продлевает сессии: их продлевает облако, через которое идут все записи. Web узла не поднимает pg-boss.
- **Сброс кэшей и realtime.**
  - `LISTEN`/`NOTIFY` на реплике не работают. Сейчас на них построены сброс кэшей (`packages/core/src/cache-bus.ts`: настройки, роли, контексты, вебхуки, языки, провайдеры входа) и события `/api/realtime`.
  - У шины появится второй транспорт: на узле события приходят одним потоком из облака (`/api/node/stream`), каждое с LSN.
  - Узел применяет событие только после того, как реплика A дошла до этого LSN, иначе кэш перечитал бы старые данные.

### Файлы

- **Ключи.** В хранилище лежат `blobs/<xx>/<uuidv7>` (после загрузки не меняются) и `mod/<модуль>/…` (распакованные SCORM и H5P, HLS-видео).
- **Драйвер зеркала.** У узла свой драйвер хранилища `mirror`: файл берётся с локального диска, а недостающий скачивается из облака через API узлов и остаётся на диске.
- **Предзагрузка.** Агент заранее скачивает всё: список блобов из таблицы `FileBlob` реплики A и ключи `mod/` по списку облака. Сначала идут файлы курсов, которые недавно открывали.
- **Удаление.** Файлы, удалённые в облаке, удаляются и с узла.
- **Скачивание на узле.** Права проверяются по базе A, файл отдаётся из зеркала без подписанных ссылок S3. В `serveFile` нужно добавить поддержку Range, сейчас её нет.
- **Домен контента.** На узел направляется и домен контента (`CONTENT_HOST`, SCORM и H5P). Его токены подписаны `APP_SECRET`, поэтому подходят и облаку, и узлу.
- **Загрузки.** Пока связь есть, они идут в облако. Без связи — в зеркало, а при синхронизации передаются в облако раньше операций, которые на них ссылаются.

### Автономный режим

- **База.** Агент делает реплику B главной (`pg_promote`), и web с воркером переходят на неё. В web два пула соединений, нужный выбирается на каждый запрос по режиму узла, перезапуск не нужен. На B работают `LISTEN`/`NOTIFY`, поэтому сообщения и уведомления в реальном времени работают внутри сети.
- **Журнал операций.** Каждое изменение записывается в таблицу `NodeOp` в той же транзакции. В записи:
  - имя и версия операции, вход, действующее лицо и время;
  - созданные ID и использованные случайные значения;
  - ссылки на файлы;
  - для операций с проверкой — версии строк, которые операция меняла.
- **Фоновые задачи.** Воркер на B выполняет только внутренние задачи:
  - закрытие просроченных попыток и переключение этапов семинара. В журнал они не попадают: облако придёт к тому же само (см. «Детерминированные операции»);
  - пересчёт оценок и выполнения — эти не записываются, облако пересчитает их само;
  - уведомления внутри приложения.

  Задачи с внешними действиями не выполняются: почта, push, вебхуки, AI, LDAP, внешние календари, BBB. После воспроизведения они возникнут в облаке заново.
- **Страж.** Любая запись в базу вне операции из журнала в автономном режиме — ошибка. Её ловит расширение Prisma: в тестах она роняет тест, в работе пишется в журнал и показывается на странице состояния узла.

### Воспроизведение в облаке

- **Порядок.** Сначала файлы, потом операции по порядку, пачками. Каждая операция идемпотентна по своему ID, облако хранит её результат. Связь может снова оборваться посреди синхронизации, и повтор ничего не задвоит.
- **Контекст.**
  - Действующее лицо берётся из журнала. Пользователь должен существовать и не быть заблокированным.
  - Время берётся из журнала. Оно должно лежать в окне обрыва, которое облако знает по сигналам узла, иначе пришлось бы верить задним числам.
  - k-я созданная строка модели M получает k-й записанный ID этой модели. Так ссылки и адреса, которые видели люди, остаются верными.
  - Случайные значения (например, порядок вопросов теста) берутся из журнала.
- **Права и правила.** Облако проверяет их как обычно. Если студента за это время отчислили с курса или тему закрыли, операция отклоняется.
- **Политика у каждой операции.** Задаётся рядом с её определением, и тест следит, чтобы она была у всех:
  - `replay` — добавление: попытки, сдача работ, сообщения форума, записи, просмотры, выполнение, данные SCORM и H5P. Воспроизводится как есть.
  - `guarded` — правка существующего: оценки, отзывы, содержимое и настройки курса. Облако сначала проверяет, что изменённые на узле строки в облаке с тех пор не менялись. Иначе это конфликт, и в отчёт попадают обе версии.
  - `online` — без связи недоступно. Сюда относятся пользователи, роли, записи на курсы, настройки сайта, модули, способы входа, резервные копии и импорт, смена пароля и всё, чему нужен интернет.
- **Закрытие просроченных попыток.** В облаке оно и переключение этапов семинара ждут конца воспроизведения (advisory lock). Иначе они закрыли бы попытку раньше, чем дойдут её ответы.
- **Возврат к обычному режиму.** Узел ждёт, пока A догонит облако, переходит на A и в фоне пересоздаёт B из A локальным `pg_basebackup`.
- **Конфликты.**
  - Администраторы видят их на странице «Узлы → Конфликты», преподаватель — по своим курсам.
  - Автор получает уведомление, а содержимое отклонённой операции сохраняется.
  - Отклонённую работу учащегося (попытку теста, сданное задание) преподаватель может принять вопреки правилу, например сверх лимита попыток. Работа, сделанная без связи, не теряется.

### Несколько узлов

- **У каждого узла всё своё:** запись в облаке с названием (филиал, корпус), токен и сертификат, слот репликации, поток событий и журнал операций. ID операций уникальны по всем узлам.
- **Адрес.**
  - Внутренний DNS каждого филиала направляет один и тот же адрес LMS на свой узел.
  - Ноутбук, который переносят между филиалами или домой, работает под тем же адресом, а сессия действует везде.
  - Сертификат у всех узлов один, поэтому его удобно раздавать из облака.
- **Порядок воспроизведения.** Облако принимает журналы по одному узлу за раз, в порядке возвращения связи.
  - Если недоступно было само облако, после его возвращения журналы всех узлов встают в эту очередь.
  - Действия с разных узлов сталкиваются по тем же правилам, что действия узла и облака: `replay` применяется, `guarded` сверяет версии.
  - Пример: студент без связи прошёл один и тот же тест в двух филиалах и превысил лимит попыток. Лишняя попытка попадает в конфликты, и преподаватель решает, принять ли её.
- **Файлы.**
  - По умолчанию узел копирует все файлы облака.
  - Для филиала с небольшим диском копию можно ограничить категориями курсов. Остальные файлы при связи кэшируются при первом открытии, а без связи недоступны.
  - Облако ограничивает скорость, с которой отдаёт файлы узлам. Иначе первичная загрузка нескольких узлов забьёт канал, через который работают учащиеся из дома.
- **Управление.**
  - На странице «Узлы» видны все узлы: режим, отставание реплики, ход копирования файлов, журнал обрывов, конфликты.
  - Администратор сайта назначает администраторов конкретного узла (право `node:manage`). Они видят состояние своего узла, включают автономный режим и откладывают синхронизацию, но не администрируют сайт.
- **Экзамены в аудитории.** Правило доступа к тесту «только через узлы …» с выбором узлов: экзамен открывается только в аудиториях конкретного филиала.
- **Происхождение действий.** Операции и журнал событий хранят узел, с которого пришло действие. Отчёты можно фильтровать по филиалу.
- **Данные филиалов.** Физическая репликация копирует базу целиком, поэтому на каждом узле лежат данные всех филиалов. Разделить базу по филиалам можно только логической репликацией с фильтрами. Это отдельная большая работа, в план она не входит.
- **Долго молчащий узел** держит WAL в облаке до предела `max_slot_wal_keep_size`. Когда предел пройден, узел пересоздаёт A, а если филиал закрылся, администратор удаляет узел и его слот.

### Детерминированные операции

Чтобы облако получило тот же результат, что и узел, операции должны зависеть только от входа, состояния базы и контекста. Сейчас это не так:

- **Записи вне операций.** Около 195 операций (`defineOperation`) и действия модулей (`runModuleAction`) проходят через два исполнителя, но реестра операций по имени нет. Вне исполнителей пишут:
  - HTTP-маршруты модулей: `commit` в SCORM, `xapi` в H5P, LTI, обратные вызовы вебинаров;
  - хуки входа;
  - около 90 мест в обработке запросов.
- **Время.**
  - В `packages/core` около 80 вызовов `new Date()` и 23 вызова `Date.now()`, а `ctx.now` используется в 48 местах.
  - Мимо `ctx.now` идут и сроковые времена: `gradedAt` (`packages/core/src/grades/gradebook.ts:257`), время выполнения (`packages/core/src/completion/completion.ts:49,90,93,204`).
  - Ещё их дают столбцы с `@default(now())`: начало попытки SCORM, `EventLog.createdAt`, `issuedAt`, `acceptedAt`.
- **ID.** У 123 моделей `@default(uuid(7))`, их создаёт клиент Prisma в JS. Ещё есть явные `uuidv7()` и `generateId` в Better Auth.
- **Случайность.** Порядок вопросов теста задаётся через `Math.random` (`modules/quiz/src/server.ts:476`). Так же выбирается страница лекции, распределяются работы в семинаре и импортируются группы.

Что меняется:

- Появляется реестр операций по имени и версии.
- Каждая запись в базу принадлежит области записи (`withWriteScope` в `packages/db`). Область говорит, что узел делает с записью:

  | Область | Что это | Узел при связи | Узел без связи |
  |---|---|---|---|
  | `operation` | операции и действия модулей | пересылает в облако | пишет и заносит в журнал |
  | `touch` | побочные записи просмотра (функция `touch` в `packages/core`) | отправляет в облако пачками | пишет и заносит в журнал |
  | `auth` | собственные таблицы Better Auth | пересылает `/api/auth` в облако | вход заносит в журнал, остальное только при связи |
  | `derived` | данные, которые можно пересчитать | не пишет: пересчитывает облако | пересчитывает на B, облако потом заново |
  | `files` | реестр блобов и сессии загрузки | пересылает загрузки в облако | пишет, а при синхронизации передаёт файлы первыми |
  | `external` | обмен с внешними системами: AI, инструменты LTI, вебинары | маршруты обслуживает только облако | недоступно |
  | `job` | задачи воркера | не выполняет | выполняет только внутренние задачи |
  | `system` | запуск, сид, команды CLI | — | — |

- Действия людей, которые сейчас пишут в базу напрямую, становятся операциями. Это данные SCORM и H5P, загрузки файлов, профиль и личные настройки, подписки на push, принятие политик, API-токены, календарь и другие, полный список — в приложении.
- Просмотр SCORM больше не создаёт попытку, её создаёт операция запуска. Так же GET перестаёт создавать журнал оценок курса, категорию банка вопросов и номера участников при слепой проверке: их создают операции.
- Страж записей (`HUBIUM_WRITE_GUARD`) в режиме `strict` отказывает в записи вне области. С ним идут тесты и e2e-сценарии, поэтому новых записей в обход не появится.
- У операции есть своё время и свои случайные числа.
  - Время — `ctx.now`, а глубже, где контекста нет, — `opNow()`. Случайные числа берутся из генератора с зерном: `ctx.random` в модулях, `opRandom()` в ядре. Оба живут в области записи операции, и вложенные области их наследуют.
  - Тест-храповик (`packages/core/src/clock-calls.test.ts`) считает `new Date()`, `Date.now()` и `Math.random()` в ядре и модулях. Новый вызов проходит, только если ему дали причину: срок жизни ссылки, задача по расписанию, чтение.
  - ID и столбцы с `@default(now())` и `@updatedAt` из контекста переносятся на этап 4, к журналу. Только там они нужны, и только там их проверит двойной прогон. В описании моделей Prisma 7 нет значений по умолчанию, поэтому понадобится генератор этого описания по схеме.
- Задачи по расписанию, меняющие видимое людям состояние, в журнал не попадают: облако приходит к тому же состоянию само.
  - Просроченную попытку теста или лекции закрывает либо задача облака, либо следующий старт, и в обоих случаях задним числом, на момент окончания времени. Старт теста закрывает просроченную попытку сам, как это уже делала лекция. Поэтому старт новой попытки, сделанный на узле, облако воспроизведёт как старт новой.
  - Этапы семинара, истечение записи на курс и публикация объявлений зависят только от времени.
  - Если правило облака уже изменилось по времени (этап семинара сменился за время обрыва), операция с узла уходит в конфликты, и преподаватель решает, что с ней делать.

Поведение от этого не меняется, поэтому изменения идут в `main` по частям. Попутно тесты становятся детерминированными.

### Вход и сессии

- **При связи** вход идёт через облако, сессия приходит на узел репликацией. После входа узел ждёт нужную позицию WAL.
- **Без связи** вход проверяется по базе B: пароль, двухфакторный код, LDAP в локальной сети.
  - Создание сессии — операция журнала (`auth.session.create`). Облако воспроизводит её с тем же токеном, поэтому после возврата на A человек остаётся в системе.
  - Счётчики блокировки входа местные.
  - Смена и сброс пароля, настройка двухфакторного входа — только при связи.

### Сеть, адреса, сертификаты

- **Соединения.** Узел только сам подключается к облаку: HTTPS и репликация PostgreSQL по TLS с клиентским сертификатом.
- **DNS.** Внутренний DNS направляет на узел адрес LMS и домен контента. `S3_PUBLIC_URL` не переопределяется.
- **Сертификаты.** Сертификат и ключ для этих имён узел получает из облака (их выпускает Caddy облака) и обновляет раз в сутки. Альтернатива — DNS-01 у регистратора, выбор после прототипа.

### Версии и обновления

- **Одна сборка.** Облако и узел работают на одной сборке: схема базы приходит репликацией, а ID server actions принадлежат сборке.
- **Обновление узла.** Агент узла следит за версией облака и обновляет узел после него. Пока версии расходятся, узел просто пересылает все запросы в облако.
- **Обновление облака во время обрыва.** В журнале записаны версии операций. Если облако обновили, пока узел был без связи, операции с несовместимым входом уходят в конфликты. `install-hubium.sh upgrade` предупреждает, если какой-то узел без связи.
- **Совместимость PostgreSQL.** Физической репликации нужны одна версия PostgreSQL, одна архитектура и одна glibc. Поэтому узел ставится только в Docker с тем же образом PostgreSQL, что в Hubium, а установщик проверяет совместимость с облаком.
- **Внешняя база облака.** Облако на внешнем управляемом PostgreSQL без доступа к репликации не поддерживается.

### Безопасность и персональные данные

- **Защита узла.** На узле полная копия базы, включая персональные данные и хэши паролей. Нужны закрытое помещение, шифрование диска и ИБП. Узел регистрируется в облаке и отзывается одним действием: токен, сертификат и слот репликации.
- **Что облако принимает от узла.** Действующее лицо и время — только в окне обрыва. Каждая операция проверяется правами этого пользователя, поэтому через узел нельзя сделать больше, чем мог сам человек.
- **IP клиента.** Запросы, пересланные узлом, подписаны, IP клиента передаётся дальше, поэтому ограничения тестов по сетевым адресам работают.
- **Новое правило доступа к тестам:** «только через узлы …», то есть экзамен только в аудиториях выбранных филиалов.
- **Объём WAL.** Предел слота `max_slot_wal_keep_size` защищает диск облака. Если обрыв дольше, узел заново создаёт A из полной копии базы.

### Состояние этапов 0 и 2–6

- **Этап 0.** Стенд `e2e/node/stack.ts`: облако и два узла на одной машине, между ними каналы, которые сценарии рвут. Прототип проверил репликацию A по TLS, каскадную B, повышение B, пересоздание копий и потерю слота.
- **Этап 2.** Готово: роль узла, агент со шлюзом, ожидание LSN, подписанная пересылка с IP клиента, шина облака, регистрация по коду, «Администрирование → Узлы», администраторы узла, установка (`install-hubium.sh --node`, `enable-nodes`). Весь e2e-набор через узел ещё не прогонялся.
- **Этап 3.** Готово: драйвер `mirror`, предзагрузка по категориям, ограничение скорости, Range, домен контента узла. Сценарий «файлы без связи» проходит.
- **Этап 4.** Готово: повышение B, режимы и переходы, журнал в транзакции операции, ID, время и случайность из операции, вход без связи, задачи узла без связи, плашки. Сценарии «тест при обрыве», «вход и форум без связи» проходят со стражем `strict`.
- **Этап 5.** Готово: очередь воспроизведения по одному узлу, идемпотентность, окно времени, проверки `guarded`, ожидание закрытия попыток, конфликты с уведомлениями, принятие преподавателем, возврат на A и пересоздание B. - **Этап 6.** Готово: обновления вслед за облаком (`hubium-node-update.timer`), метрики узлов в `/api/metrics`, журнал обрывов в карточке узла, сертификаты из облака, правило теста «только через узлы», фильтр журнала событий по узлу, документация (`architecture.md` §1.7, `operations.md`, глава администратора). Сценарии узлов идут в CI на каждый push.
- **Осталось:** ночной прогон всего e2e-набора через узлы и установка узла на чистый сервер по инструкции с полным занятием без связи (пилот в колледже).

## Тестирование

- **Модульные тесты:** реестр и политики, расширение Prisma (ID, время), движок воспроизведения (идемпотентность, окно времени, `guarded`, отказ по правам).
- **«Только чтение»:** e2e-набор против узла в онлайн-режиме, где у пользователя базы права только на чтение. Ни одной ошибки записи.
- **«Двойной прогон»:** e2e-сценарии на узле без связи, затем синхронизация. Видимое людям состояние в облаке должно совпасть с узлом.
- **Обрывы:** во время теста, во время загрузки файла, посреди синхронизации, частые короткие обрывы, обрыв дольше предела WAL, параллельные действия того же студента из облака, обновление облака во время обрыва.
- **Несколько узлов:** один и тот же студент без связи в двух филиалах; два узла без связи, пока в облаке меняют те же данные; недоступность облака, когда без связи все узлы, а потом все возвращаются одновременно.
- **CI:** compose с облаком, двумя узлами и переключением сети между ними. Короткие сценарии — на каждый коммит, длинные — ночью.

## Требования к узлу

- **Сервер:** Linux x86_64 или arm64, та же архитектура, что у облака. От 4 ядер и 8 ГБ памяти.
- **Диск:** база ×2 (A и B), плюс все файлы облака, плюс запас под WAL. ИБП.
- **ПО:** Docker Engine 24+ и Compose 2.20+.
- **Сеть:** исходящий HTTPS и порт репликации PostgreSQL облака.
- **Внутренний DNS:** адрес LMS и домен контента указывают на узел.

Облаку с каждым новым узлом нужно больше:
- **Канал** на первичную загрузку узла (база и файлы) и на поток изменений.
- **Диск** под WAL, который держат слоты молчащих узлов, до предела `max_slot_wal_keep_size`.

## Риски

| Риск | Что делаем |
|---|---|
| Запись в обход журнала теряет работу, сделанную без связи | Страж в автономном режиме, тест «только чтение», двойной прогон в CI |
| Облако получает при воспроизведении другой результат | Время, случайные числа и ID операции из контекста, тест-храповик, двойной прогон |
| Первичная копия базы и файлов по плохому каналу | Файлы докачиваются, копия базы повторяется. Для больших баз — начальная копия с носителя |
| Первичная загрузка нескольких узлов забивает канал облака | Ограничение скорости в облаке, начальная копия с носителя |
| На каждом узле данные всех филиалов | Физическая защита и шифрование диска на каждом узле, отзыв узла одним действием |
| После недоступности облака все узлы возвращаются разом | Очередь воспроизведения по одному узлу, закрытие попыток в облаке ждёт конца очереди |
| Обрыв дольше предела WAL | Узел сам пересоздаёт A, администратор видит это на странице «Узлы» |
| Узел и облако на разных версиях | Пересылка всех запросов, пока версии расходятся, версии операций в журнале |
| Синхронизация посреди занятия | Ждём конца тестов с ограничением времени, администратор может отложить синхронизацию |

## Открытые вопросы

1. Две базы на узле (A и B, вдвое больше диска, без простоя при возврате) или одна с `pg_rewind` (простой на время перемотки). Решено: две, прототип это подтвердил.
2. Сертификаты для узлов: передавать из облака или DNS-01. Решено: из облака (`GET /api/node/cert`); узел с собственными именами получает свой сертификат.
3. Порог автоматического перехода в автономный режим. Решено: две минуты по умолчанию, `NODE_OFFLINE_AFTER` меняет.

## Приложение: записи вне операций (этап 1)

Список собран по коду на версии 1.0.0-rc.3. Пути — от корня репозитория. Номера строк сдвигаются по мере правок, поэтому ориентир — имя функции.

### Побочные записи просмотра → `touch`

- `noteUserAccess` в `apps/web/src/server/session.ts` (последний заход) и `lastUsedAt` токена с `noteUserAccess` в `authenticateApiToken` (`packages/core/src/api-tokens/tokens.ts`).
- Страница курса: `recordCourseAccess`. Страница элемента: `markActivityViewed`, `recordCourseAccess`, `logEvent('activity.viewed')` (`apps/web/src/app/(app)/course/[courseId]/…`).
- Запуск инструмента LTI (`lti.launch` в журнале событий), начало сеанса проигрывателя SCORM (`sessionBaseSec`), выгрузка своих данных (`privacy.exported`).
- В хуке создания сессии: `lastLoginAt` и `lastSeenAt` известного устройства.

### Действия людей → операции

- **Учётная запись:**
  - `preferences.ts` (язык, тема) и `account.ts` (имя, часовой пояс, свои поля, снятие требования сменить пароль) в `apps/web/src/server/actions`;
  - «Это был не я» (`reportNotMe`), разблокировка по ссылке (`unlockWithToken`), отписка от писем (`applyUnsubscribe`, действие и маршрут);
  - подписки на push (`/api/push`), принятие политик (`acceptPolicies`), API-токены (`createApiToken`, `revokeApiToken`, в том числе REST).
- **Файлы:** `storeFile`/`storeFileFromPath` после операций создания и правки курса и элемента, обложка курса (`setCourseImage`), файлы редактора (`/api/files/editor`), свидетельства компетенций.
- **Перенос:** копирование курса и элемента, импорт элементов, импорт Moodle XML, запуск импорта и резервного копирования, удаление копии (`apps/web/src/server/actions/interchange.ts`, `courses.ts`, `grades.ts`).
- **AI:** согласие, запуск и разбор генерации вопросов, оценка ответа тьютора, подсказки проверки в задании (действия модуля с `mutation: false`).
- **Календарь:** новый токен ленты.
- **Администрирование:**
  - режим обслуживания (`setMaintenance`, в том числе из CLI) и запись в журнал о конце входа под другим пользователем;
  - ручной запуск и повтор задач, отправка отчёта по расписанию;
  - массовые действия с пользователями: принудительная смена пароля пишет мимо вложенных операций.
- **Модули:**
  - SCORM: `commit` с домена контента (данные, оценка, выполнение) и создание первой попытки при просмотре. Сделано: POST домена контента идёт в области `operation`, GET — в `touch`, а первую попытку создаёт первый `commit`;
  - H5P: `xapi` с домена контента (попытка, оценка, выполнение);
  - задание: номера участников при слепой проверке создавались при открытии страницы и при скачивании работ. Сделано: их выдают операции (создание задания со слепой проверкой и её включение, запись на курс через хук модуля `onUserEnrolled`, сдача работы, оценка, сброс курса) из случайных чисел операции, страницы их только читают. Старым заданиям номера выдала миграция;
  - вебинар: `join`, `end`, `syncRecordings` с `mutation: false`.
- **Ленивые значения по умолчанию:** журнал оценок курса (`ensureCourseGradebook`, вызывается со страниц оценок и из REST) и категория банка вопросов (`packages/core/src/questions/bank.ts`). Создаются операциями создания и восстановления курса, для существующих курсов — миграцией данных.
- **Атомарность:** `lti.tool.save` и `lti.key.rotate` объявлены с `mutation: false`, но пишут. Поворот ключа сейчас может оставить LTI без действующего ключа. Обе получают транзакцию.

### Вход → `auth`

- Адаптер Better Auth уже в области `auth`: сессии, учётные записи, проверки, двухфакторный вход, лимиты.
- Хуки и плагины Hubium пишут мимо адаптера, их переводим в область `auth`:
  - счётчики блокировки (`lockout.ts`), история паролей (`password-policy.ts`), фразы восстановления (`recovery.ts`);
  - вход под другим пользователем (`login-as.ts`), заглушка почты;
  - создание и обновление учётной записи при входе через LDAP и SSO.

### Производные данные → `derived`

Это кэш текста файлов (`fileText`), индекс AI, пересчёт выполнения и итогов журнала оценок с наградами, синхронизация внешних календарей, распаковка SCORM и H5P, перекодирование видео.

### Файлы → `files`

Реестр блобов (`checkFile`, `checkUpload`) и сессии загрузки (`/api/uploads`, `consumeUpload`).

### Внешние системы → `external`

- AI-тьютор: беседа, сообщения и учёт расхода пишутся по ходу ответа.
- LTI: одноразовые значения, ключ платформы, токены доступа, а также оценки и элементы, которые присылает инструмент (AGS, deep linking).
- Вебинары: обратные вызовы BBB о конце встречи и о записях, опрос посещаемости.

### Задачи воркера → `job`

- **Меняют то, что видят люди.** В журнал не попадают: облако приходит к тому же само (см. «Детерминированные операции»).
  - Закрытие просроченных попыток теста и лекции, смена этапа семинара, истечение записи на курс.
  - Публикация объявлений, выдача значков и сертификатов, синхронизация планов обучения.
  - Автозавершение вебинара, удаление исходника видео после перекодирования.
- **Внешние действия:** письма, дайджесты, push, вебхуки, напоминания, отчёты по расписанию, LDAP, опрос BBB, AI.
- **Уборка:** чистка журналов, корзины, неиспользуемых файлов, просроченных сессий и одноразовых значений LTI, сигнал работы воркера.

### Время и случайность → контекст

- **Время из `new Date()`** в столбцах, на которые смотрят люди:
  - `Grade.gradedAt`, время выполнения и просмотра элемента, начало и конец курса, доступ к курсу;
  - `lastLoginAt`, блокировка входа, смена пароля, выдача значков и сертификатов, публикация объявлений;
  - время в протоколах LTI.

  Столбцы с `@default(now())`, которые нужно заполнять из контекста: начало попытки SCORM, `EventLog.createdAt`, `issuedAt`, `acceptedAt`. В маршруте домена контента и в воркере `ctx.now` — это `new Date()` в момент запроса.
- **Случайность:**
  - `Math.random` — порядок вопросов теста (`seed`), переходы лекции, распределение работ семинара, импорт групп (сделано: `ctx.random` и `opRandom()`);
  - `randomInt` — номера участников задания (сделано: `ctx.random`);
  - `randomUUID` — ID в опросе, лекции и семинаре (сделано: `opRandom().uuid()`).
